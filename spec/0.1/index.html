0What OMF is

A memory vault is a plain folder of Markdown files (plus a few binaries and one JSON settings file) that records a person's life: journal entries and linked entities — people, places, projects, and more — connected by wikilinks.

OMF is a profile of three things developers already know:

  • CommonMark Markdown for bodies,
  • YAML frontmatter for structured fields,
  • [[wikilinks]] and ![[embeds]] for cross-references (Obsidian-compatible).

A vault is portable by construction: it is just files in a folder, in any storage the user controls (local disk, Google Drive, Dropbox, …). Any app that follows this spec can read and write the same vault.

Files come in three kinds (Section 4.3): entity (one subject per file), metric (a dated numeric table), and log (a timeline of dated sections). All three are plain Markdown with YAML frontmatter; they differ only in body shape. UTF-8, LF line endings throughout.

0.1 · Scope & non-goals

OMF is a portability / migration format: it guarantees that a vault written by one OMF app can be fully read (and taken over) by another. It is not a concurrent multi-writer protocol — two apps editing the same vault at once is out of scope, so OMF does not define merge/conflict semantics (writers may assume last-write-wins). This keeps the format simple: your data is portable, without the complexity of real-time co-editing.

1Vault layout

<vault root>/
  Journals/                 # dated entries
    YYYY/MM/YYYY-MM-DD.md
  People/<slug>.md          # entity folders (one entity per file)
  Places/<slug>.md
  Projects/<slug>.md
  Dreams/<slug>.md          # apps MAY define further collections
  Movies/<slug>.md
  Health/<metric>.md        # metric kind (Section 4.3)
  F1/<season>.md            # log kind (Section 4.3)
  Photos/                   # binary attachments (images, …)
  orma_settings.json        # vault settings + identity (Section 7)
  • Top-level folder name = the collection; for entity collections it is the singular type (Section 4).
  • One file per subject (entity) / metric / timeline; the file's slug (filename without .md) is its identity within the collection.
  • Folders an app doesn't recognize MUST be preserved untouched (forward-compat).

2Slugs

A slug is the stable file identity. Canonical slugify: (1) lowercase, (2) collapse whitespace runs to -, (3) remove anything outside [a-z0-9-], (4) trim leading/trailing -. Empty result → a folder-defined fallback (entry; me for an empty self).

Slugs are case-sensitive and lowercase. A wikilink's slug MUST match the target filename exactly (People/jane-doe, never People/Jane-Doe).

3Journal entries

Path: Journals/YYYY/MM/YYYY-MM-DD.md (hierarchical). Readers SHOULD also accept a flat Journals/YYYY-MM-DD.md; writers SHOULD use the hierarchical form.

Content is Markdown with no frontmatter. An optional leading # Heading is the entry title; everything after is the body:

# A good day

Had coffee with [[People/jane-doe|@Jane]]. Felt @grateful.

The date is carried by the filename, not the body. A journal also surfaces what you logged elsewhere that day (Section 5.6).

4Entity files & file kinds

An entity file is YAML frontmatter + an optional Markdown body (free-text "notes").

---
name: Jane's Place
type: place
address: 1 Example Street, Anytown
people:
  - "[[People/jane-doe|Jane (home)]]"
---

Optional free-text notes go here.

4.1 · Frontmatter fields

  • name (string, required) — display name.
  • type (string, required) — entity type. The folder is the primary type (People→person, …). type MAY deviate to mark a variant: self (vault owner, Section 6) or series (a TV series in Movies/).
  • scalar fields (string) — collection-specific (birthday, address, …). Unknown scalars MUST be preserved.
  • link blocks (relations, places, people) — see Section 5.

4.2 · Bodies

Everything after the closing --- is the notes body (Markdown). Apps SHOULD preserve it verbatim.

4.3 · File kinds

A collection's files are one of three kinds. All share YAML frontmatter, real YAML, lowercase slugs and Markdown bodies — they differ only in body shape, and so in how they're surfaced (Section 5.6):

KindFrontmatterBodyUsed byOne file =
entityname, type, fields, link blocksfree-text notesPeople, Places, Movies, Dreams, Projectsone subject
metricmetric, unita dated tableHealthone measured quantity
logname, type, kind: logdated ## sectionsF1, any timelineone timeline (e.g. a season)

type/metric identify the collection. The kind is given by an optional kind: entity|metric|log field; when absent it is inferred — a file with a metric: key is a metric, otherwise an entity. Because an entity's notes may legitimately contain a ## YYYY-MM-DD heading, log files MUST declare kind: log; kind is optional for entity and metric files.

The journal (Section 3) is itself a per-date log-like file, but path-addressed by date rather than section-addressed.

5Links, embeds & the timeline

OMF has one link family: [[ ]] references, ![[ ]] transclusions, and CommonMark ![ ][ ] image attachments.

5.1 · Wikilink grammar

[[<Folder>/<slug>|<display>]]
  • <Folder>/<slug> resolves to <Folder>/<slug>.md.
  • <display> is human text, optionally with a relation label in trailing parentheses: Name or Name (label).

Examples: [[People/jane-doe|Jane]], [[People/john-doe|John (home)]].

5.2 · Link blocks (relations)

A link block is a frontmatter key whose value is a YAML list of wikilink strings. The relation label is encoded in the display (the (label) suffix):

relations:
  - "[[People/john-doe|John (brother)]]"
  - "[[People/jane-doe|Jane (friend)]]"
places:
  - "[[Places/anytown|Anytown (home)]]"

Defined blocks: relations (→ People), places (→ Places), people (→ People). Apps MAY define more. Reciprocity is a within-app convention — record the inverse on the other entity, except links to the self entity (Section 6), which stay one-directional to avoid an unbounded hub file. As a migration format (Section 0.1), an importing app just reads whatever links exist.

5.3 · Mention shorthand

In journal/body text, @<slug> is a lightweight mention of an entity by slug (default collection: People), equivalent to a wikilink for backlink purposes.

5.4 · Attachments / photos

Binary attachments live under Photos/, embedded with standard CommonMark reference-style image links:

![alt text][photo-1]

[photo-1]: Photos/2026-06-27-river.jpg

Ordinary CommonMark — renders in Obsidian and any compliant engine. A reference-style image MAY be wrapped in a reference-style link ([![alt][photo-1]][open-1]) to make it clickable.

5.5 · Transclusion (section embeds)

A !-prefixed wikilink embeds the target rather than linking to it:

![[<Folder>/<file>#<heading>]]

This transcludes the section under <heading> — used to surface a log entry inside another file (notably the journal, Section 5.6). Example:

![[F1/2026-season#2026-06-29 — Austin Grand Prix]]
  • The anchor is the heading text, so headings must be unique; date-led headings (## YYYY-MM-DD — Title) are naturally unique and are REQUIRED for log sections. If a heading changes, the writing app MUST rewrite the journal embed (rewrite-on-rename). A future version MAY anchor on a stable block id.
  • Transclusion is the Obsidian embed convention, not CommonMark — it renders in Obsidian and OMF apps; a bare CommonMark engine shows it literally. (Same family as [[wikilinks]].)
  • An embed is also a backlink: "open the Austin entry → see it was embedded in the 2026-06-29 journal."

5.6 · Surfacing dated entries in the journal (the timeline)

An app MAY make an entry logged in another collection on date D appear in D's journal, turning the journal into a timeline of the day. Two mechanisms, chosen by the source file's kind:

  • Log entry → embed. Append a dated ## section to the log file and write a section embed (Section 5.5) into D's journal. Live (renders the current section) and portable (Obsidian transcludes it).
  • Metric reading → snapshot line. A table row can't be section-embedded, so append the row to the metric table and write a plain-text snapshot line into the journal, e.g. Weight — 167 lb. A point-in-time record, portable as ordinary Markdown; an app MAY additionally render the live value from the table.

Both are ordinary backlinks (Section 5.2), navigable in both directions. See Appendix D for worked examples.

6Identity (the "self")

  • Exactly one People/<slug>.md carries type: self — the vault owner.
  • orma_settings.json → user.person_slug is the authoritative pointer; user.person_name is the display name.
  • Recovery: if the pointer is missing, an app MAY scan People/ for the single type: self file and repair the pointer.
  • The self file MUST NOT accumulate auto-generated reverse links (Section 5.2).

7Settings file

orma_settings.json at the vault root, plaintext JSON:

{
  "omf_version": "0.1",
  "user":  { "person_slug": "jordan-doe", "person_name": "Jordan" },
  "apps":  { "<app_id>": { "enabled": true } },
  "nav_order": ["<app_id>", "..."]
}
  • omf_version (string, required) — the OMF version the vault conforms to (Section 8).
  • user — identity, core to OMF.
  • apps, nav_order — UI/app state; apps MUST preserve keys they don't understand.

8Versioning

A vault declares its format version via omf_version in orma_settings.json. A writer MUST set it; a reader MAY use it to detect compatibility. Absence is treated as the earliest version (0.1).

9Resolved decisions (0.1)

  • Strict YAML — frontmatter MUST be valid YAML 1.x.
  • Slugs are lowercase — writers MUST emit lowercase slugs (Section 2).
  • Attachments are standard CommonMark reference-style image links (Section 5.4).
  • Concurrency is out of scope (Section 0.1) — migration format; no merge/conflict semantics.
  • omf_version is a required settings field (Section 7–8).
  • File kinds (Section 4.3) — entity / metric / log, with an optional kind: field; log files MUST declare kind: log.
  • Embed anchors (Section 5.5) — date-led log headings; apps rewrite journal embeds on heading change.

10Open questions (to settle before 1.0)

  1. type redundancy. type echoes the folder for the default case. Keep always-present or present-only-when-deviating?
  2. Mention resolution. Which collection(s) @slug resolves against, and case rules.
  3. Settings scope. Are apps/nav_order core OMF or a namespaced app-extension block?
  4. Metadata privacy. Filenames/paths leak structure. How would a future encrypted profile handle names?

11Conformance (planned artifacts)

A 1.0 ships with: this spec, an example vault, a validator, and a reference parser library extracted from the app. The spec text is released under an open license (e.g. CC-BY-4.0); implementing OMF requires no permission.

Appendix A

Apps & collections

OMF is organized into collections — a top-level folder of files of one kind (Section 4.3). An app is a module that owns a collection: it defines the folder, the type/kind, and the field set, and provides the UI. Collections are the extension point — new apps add new folders without changing the format.

  • orma_settings.json → apps records per-app enabled state by app_id; nav_order records display order. A reader that doesn't know an app_id MUST preserve it (Section 7).
  • An app encountering a folder it doesn't recognize MUST leave it untouched — this is what lets two OMF apps with different feature sets share a vault.

A collection is self-describing enough to migrate when its files carry name + type (entities), a documented tabular shape (metric), or kind: log (log). An importing app can always fall back to name + type + raw frontmatter + Markdown body.

Appendix B

Built-in collection reference

Dates are ISO 8601 YYYY-MM-DD. "block" = a link block (Section 5.2). All fields other than name/type are OPTIONAL. Unknown fields MUST be preserved.

Journals · Journals/

  • File: Journals/YYYY/MM/YYYY-MM-DD.md (flat accepted on read).
  • No frontmatter. The date is the filename.
  • Optional leading # Heading = title; the rest is the body.
  • Body may contain wikilinks, @slug mentions, image attachments (Section 5.4), and journal-surfacing embeds / snapshots (Section 5.6).

Health · Health/ — metric kind (tabular)

One file per metric: small frontmatter + a Markdown table body.

---
metric: weight
unit: kg
---

| date | value | unit | notes |
|------|-------|------|-------|
| 2026-06-19 | 167 | lb |  |
  • File: Health/<metric-slug>.md.
  • Frontmatter: metric (string), unit (default unit).
  • Body: a Markdown table — header row, then one row per reading. Rows whose first cell isn't an ISO date are ignored.
  • Journal surfacing: a reading is mirrored into its date's journal as a snapshot line (Section 5.6, Appendix D). The table stays the source of truth for charts.

Logs · e.g. F1/ — log kind (dated sections)

The general timeline shape: a collection of log files, each a sequence of dated ## sections. F1 is one instance — one file per season:

---
name: 2026 Season
type: f1
kind: log
---

## 2026-03-16 — Bahrain Grand Prix
Verstappen pole to flag. Norris P2.

## 2026-06-29 — Austin Grand Prix
Wet start, three safety cars. Leclerc won from P4.
  • File: <Collection>/<slug>.md (e.g. F1/2026-season.md).
  • Frontmatter: name, type, kind: log (required).
  • Body: sections headed ## YYYY-MM-DD — Title (date-led for stable, unique anchors); section body is free Markdown.
  • Journal surfacing: an entry is embedded into its date's journal via a section transclusion (Section 5.5, Appendix D).

Appendix C

Implementer guidance

A minimal OMF reader

  1. Read orma_settings.json for omf_version and the user identity.
  2. Enumerate top-level folders. For each known collection, list *.md files.
  3. Parse each file: split the leading ---…--- frontmatter (valid YAML) from the body. Slug = filename without .md. Determine kind (Section 4.3).
  4. Resolve [[Folder/slug|Display]] wikilinks and ![[file#heading]] embeds; treat @slug as a People mention; render attachments from Photos/.
  5. For an unknown collection, fall back to name + type + raw frontmatter + body, and preserve the files unchanged.

Hard rules for any writer

  • Preserve everything you don't model — unknown folders, files, frontmatter keys, bodies. Mutate only what you change. (Comments and key order are not guaranteed across a rewrite; data is.)
  • Emit valid YAML and lowercase slugs.
  • Stamp omf_version when you write settings; kind: log on log files.
  • Use ISO YYYY-MM-DD dates; rewrite journal embeds on heading change.

Adding a new collection (new app)

  1. Pick a folder name and a singular type (and kind if metric/log).
  2. Store one entity/metric/log per file with the required frontmatter.
  3. Optionally register an app_id in orma_settings.json → apps.
  4. Existing OMF apps preserve your folder; a generic reader can already display it.

Appendix D

Journal surfacing — worked examples

Both show what's on disk after logging an entry on 2026-06-29.

D.1 · Log entry (F1) — section embed

F1/2026-season.md — the section is appended (source of truth):

---
name: 2026 Season
type: f1
kind: log
---

## 2026-06-29 — Austin Grand Prix
Wet start, three safety cars. Leclerc won from P4.

Journals/2026/06/2026-06-29.md — an embed is inserted:

Caught the race after lunch.

![[F1/2026-season#2026-06-29 — Austin Grand Prix]]

Rendering 2026-06-29: your prose, then the embedded F1 section (Orma styles it as a race widget; Obsidian transcludes the same section). Editing the race text updates everywhere it's embedded — one source of truth.

D.2 · Metric reading (weight) — snapshot line

Health/weight.md — a row is appended (source of truth, chartable):

---
metric: weight
unit: kg
---

| date | value | unit | notes |
|------|-------|------|-------|
| 2026-06-29 | 167 | lb |  |

Journals/2026/06/2026-06-29.md — a snapshot line is inserted:

Caught the race after lunch.

Weight — 167 lb

Rendering 2026-06-29: the journal shows the snapshot line (Obsidian shows plain text; Orma MAY render it as a chip and/or refresh from the live table). A table row can't be section-embedded, so the value is a point-in-time snapshot — the correct semantics for a journal: it records what you logged that day.
